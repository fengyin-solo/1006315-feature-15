# 城市地下综合管廊运行维护管理平台

面向管廊主体台账、入廊管线登记、廊内环境监测、通风排水消防、结构沉降与渗漏处置、巡检检修与隐患整改、入廊作业审批和运维值班的一体化城市地下综合管廊运行维护管理工作台。

这是一个**纯前端**管理平台：Vue 3 + Vite + TypeScript，仓库里没有后端服务。业务数据由
`frontend/src/data/` 下的本地数据层提供：首次打开用示例数据播种，之后的登记、筛选与状态流转
结果都持久化在浏览器 `localStorage` 里，刷新或重开浏览器都还在。dev server 已关掉自动打开页面，
启动后按终端打印的地址手工打开。

## 目录结构

```text
.
├── frontend/                 Vue 3 + Vite + TypeScript 前端（唯一运行单元）
│   ├── src/views/            每个业务模块一个页面
│   ├── src/api/local-service.ts   本地数据服务：列表、筛选、动作流转、导出
│   ├── src/data/             模块元数据 / 示例数据 / localStorage 持久化
│   ├── src/stores/           会话与筛选状态
│   └── vite.config.ts        dev server 配置（open: false，无 /api 代理）
├── .gitignore
└── docker-compose.yml
```

## 启动

```bash
cd frontend
npm install
npm run dev
```

前端默认监听 `http://127.0.0.1:5173/`，dev server 不会自动打开浏览器，需要自己访问。

生产构建：

```bash
cd frontend
npm run build
```

## 约定

- 每个模块的页面在 `frontend/src/views/<模块>/index.vue`，页面只负责渲染，读写统一走
  `frontend/src/api/local-service.ts`。
- 字段、状态、动作与流转目标集中在 `frontend/src/data/modules.ts`；示例数据在
  `frontend/src/data/seed.ts`。
- 状态流转只允许在 `local-service.ts` 里改，页面组件不做业务判断。
- 想回到初始数据：清掉浏览器里 `urban-utility-tunnel:entries` 这一项，或调用 `resetModule(模块)`。

## 结构沉降整组处理口径

测绘队一次交几十个断面的观测成果，结构沉降模块按「整组」处理：同一测次一次提交，
逐条回执；预检通过才落库；超阈值自动挂预警并回写设施检修清单。领域规则集中在
`frontend/src/data/settlement.ts`（纯函数），读写与并发在
`frontend/src/api/local-settlement.ts`，页面不做业务判断。可运行
`cd frontend && npm run test:settlement` 跑规则与并发测试。

### 一次提交、逐条回执

- 页面入口：结构沉降监测 →「整组提交观测成果」。测绘队的表（CSV 或从 Excel 复制的制表符
  文本）直接粘进弹窗，按「测次编号」归为同一组。
- 组内每条各出一条回执：成功写明判定结论，**没交成的逐条另起一行说明原因**（重号、重复、
  日期缺失等），不做整批一句带过。
- 一个批次同时登记一笔值班台账（运维值班交接），写清本批入账数、超限数、检修待办数、
  资料待补数。

### 提交前检查（检查通过才落库）

点「提交前检查」先列问题，硬伤清零后「整组落库」按钮才可点：

| 级别 | 情形 | 处理 |
| --- | --- | --- |
| 拦截 | 测次编号缺失、空组、监测编号为空、监测断面为空、监测日期缺失、累计沉降量缺失或非数字、阈值缺失且点位台账无此点 | 整批不落库 |
| 提示 | 批内监测编号重号、同断面同测次重复 | 允许提交，落库时只认第一条，其余逐条挡回 |
| 可后补 | 沉降速率未誊、成果行未带阈值但台账有 | 入账同时把缺失项登记进待补清单 |

### 同断面同测次只算一次 / 并发兜底

- 去重用两个键同时守：**断面+测次**（业务口径：一个断面一测次一行）与**监测编号+测次**
  （同一行被两笔同时提交）。任一键命中，只认先落库的那一笔，后一笔按重复挡回，先落的值
  不被覆盖，也不得借重复行补挂预警。
- 纯前端没有数据库行锁，服务层用一个 Promise 提交队列把「预检-落库」串成原子段，并在内存
  草稿上判定、通过才一次性写回 localStorage（`scripts/test-concurrent.mjs` 验证）。
- 回写检修清单用 `SETT#监测编号#测次编号` 幂等键，重试/并发不会产生第二条待办。

### 超限预警与检修联动

- 新口径下累计沉降量按**绝对值**与阈值比较：`|累计沉降量| > |阈值|` 即挂「超限预警」
  （沉降量正负号只是方向，比较位移大小）。
- 预警断面在设施检修管理清单生成一条「待安排」记录（检修类别=沉降超限预警，检修班组=待安排，
  附预警结论、来源批次/测次），检修页面顶部红条优先提示；安排班组后走检修原有状态流。
- 成果行未带阈值时从**点位台账**取阈值兜底；台账也没有则属预检拦截项。

### 新老口径切换与存量回填

- 切换日常量为 `SWITCH_DATE = 2026-10-06`（上线日，可在 `src/data/settlement.ts` 调整）。
  **监测日期 ≥ 切换日**走新口径（系统自动判定、自动联动）；**早于切换日的测次一律沿用原
  结论，不重新判定、不补挂预警、不生成检修待办**，明细行标记「旧口径（沿用原结论）」。
  依据：历史结论是当时人工签认的，系统不应拿新阈值倒翻旧账；新口径只约束切换后的提交行为。
- 存量两条回填路径，**先后顺序定为：先点位台账（按设备投运日期），后观测成果（按监测日期）**。
  依据：成果判定依赖阈值，而阈值挂在点位台账上；先建台账才能给缺失阈值的成果行兜底。
  - 点位回填：按投运日期建点；点已存在且阈值不一致时**不覆盖**，转待补清单由人工裁决，
    避免新老阈值互相冲掉。
  - 成果回填：用「存量成果按监测日期回填」方式提交（批次号前缀 `BF-`，正常提交为 `BC-`），
    旧测次落到原结论；沉降速率等未誊项进待补清单。
- 缺失项集中列在「待补清单」页签（区分来源路径、缺失项、批次），补录后只标记「已补录」，
  不回改历史结论。

### 对账与报表

- 「测次汇总与对账」页签按批次把预警数、检修新增数、资料待补数与值班台账逐条核对，并给出
  总量核对（检修待安排数 = 台账检修待办登记数；待补录数 = 台账资料待补登记数），有差异会
  逐批列出。
- 测次汇总（状态分布）与观测明细共用同一份数据源与同一套汇总函数
  （`summarizeRounds`），导出的「测次汇总报表」末尾附对账行，页面读数与 CSV 报表读数一致。
